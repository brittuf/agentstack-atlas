LendingTree: how the agent works and how to build one like it

Summary: LendingTree built a multi-agent mortgage assistant using a supervisor agent that delegates to worker agents, built with LangGraph and MCP. The source reports over 97% of conversations are handled without escalation.

Source: https://aws.amazon.com/blogs/machine-learning/how-lendingtree-built-a-multi-agent-mortgage-assistant-on-amazon-bedrock/ source read via search extract

Why this use case works

The supervisor-and-workers design keeps each worker narrow (rates, eligibility, application status, education), which makes them easier to test and lets the supervisor focus on routing. MCP gives the workers a standard way to reach internal tools instead of one-off integrations. (Our analysis.)

Agent pattern: Support chat agent

A support chat agent: a retrieval layer over help-center and policy content, tool calls into the systems of record (billing, orders, accounts), and explicit escalation rules. The quality of the knowledge base matters more than the model choice.

How a smaller team could replicate it

Teams with several distinct question types can start with a router plus two or three specialist agents in LangGraph or a similar framework, each with its own tools and test set, and add workers only when a question category is large enough to justify one. (Our analysis, not a claim made by the source.)

Risks and guardrails

Risks: a supervisor that routes wrongly sends confident but irrelevant answers, and financial-rate questions carry disclosure obligations. Guardrails: per-worker test sets, logged routing decisions, and approved compliance language for rate and eligibility answers. (Our analysis.)

What to measure

Escalation rate, routing accuracy (did the supervisor pick the right worker), answer correctness on a labeled test set, and conversion from conversation to application.
